# Конституция проекта «Заявки на оборудование»

## Core Principles

### I. Спецификация — источник истины
Изменение поведения системы ДОЛЖНО начинаться с `spec.md`. Код меняется только через цикл
specify → plan → tasks → implement (spec-anchored): правка кода в обход спецификации не считается
выполненной работой. Если код и спецификация расходятся, правим спецификацию и пересобираем цикл,
а не «подгоняем» код молча.
<!-- Rationale: без этого спека превращается в черновик, а «правда» живёт в коде и в голове агента. -->

### II. Без новых зависимостей
`build.gradle` НЕ ДОЛЖЕН меняться. Если для задачи нужна библиотека, обоснование записывается в
`plan.md` (раздел Complexity Tracking), а решение о подключении принимает человек, не агент.
<!-- Rationale: каждая зависимость — это поверхность атаки, лицензия и риск несовместимости со стартером Jmix. -->

### III. Только собственные `@RestController` под `/api/**`
Внешний интерфейс строится на собственных `@RestController` в путях `/api/**`. ЗАПРЕЩЕНЫ: аддон
Generic REST (`jmix-rest-starter`), REST DataStore, Authorization Server. Каталог `security/**` и
класс `ApiSecurityConfiguration` НЕ ДОЛЖНЫ изменяться.
<!-- Rationale: цепочка безопасности для /api/** уже настроена и проверена; чужие аддоны открывают лишние эндпоинты. -->

### IV. Схема БД — только новыми Liquibase changeSet'ами
Любое изменение схемы оформляется НОВЫМ changeSet'ом (новый файл в
`com/debugskills/equipment/liquibase/changelog/` и `<include>` в `changelog.xml`). Существующие
changeSet'ы НЕ ДОЛЖНЫ редактироваться.
<!-- Rationale: правка применённого changeSet'а ломает контрольные суммы Liquibase на уже развёрнутых базах. -->

### V. Контекст по этапам
Полную документацию Jmix (`docs/jmix/jmix-complete-docs.adoc`) читает только этап plan, через
`docs/jmix/INDEX.md` и по диапазонам строк. У каждого Jmix-решения в `research.md` ДОЛЖНЫ быть
**Snippet** (фрагмент кода, достаточный для реализации) и **Source** (раздел документации и строка).
Implement работает по `research.md`, `data-model.md`, `contracts/` и тематическим `docs/jmix/*.md`;
полную документацию он не открывает. Если в `research.md` чего-то не хватает, implement выводит
`GAP` и останавливается: это дефект плана, и правка вносится через `/speckit.plan`, а не догадкой
в коде.
<!-- Rationale: короткий, проверяемый контекст на исполнении дешевле и надёжнее, чем 85 тысяч строк документации. -->

### VI. Наружу — только DTO
Контроллеры принимают и возвращают DTO. Сущности Jmix НЕ ДОЛЖНЫ попадать в тело запроса или ответа
и в контракты в `contracts/`.
<!-- Rationale: сущность Jmix тянет за собой служебные поля, ленивые связи и внутреннюю модель данных. -->

### VII. Каждый сценарий Given/When/Then — тест
Каждый сценарий приёмки Given/When/Then из `spec.md` ДОЛЖЕН быть покрыт автоматическим тестом.
`./gradlew test` ДОЛЖЕН быть зелёным до закрытия задачи; удалять или ослаблять существующие тесты
ради зелёной сборки ЗАПРЕЩЕНО.
<!-- Rationale: тест — единственное исполнимое доказательство того, что спецификация выполнена. -->

## Что не входит в конституцию

<!-- Что НЕ кладём в конституцию (говорим в интро лабы):
     требования конкретной фичи, вкусовые правила стиля, списки «хороших библиотек»,
     пересказ документации. -->

Конституция хранит только устойчивые правила, общие для всех фич проекта. В неё НЕ кладутся:

- требования конкретной фичи (они живут в `spec.md`);
- вкусовые правила стиля и форматирования;
- списки «хороших» библиотек (по принципу II новые зависимости не добавляются);
- пересказ документации Jmix (он живёт в `docs/jmix/`).

## Governance

Конституция имеет приоритет над остальными практиками проекта. Конфликт с конституцией на этапе
plan — блокирующая ошибка: либо план исправляется, либо нарушение явно обосновывается в разделе
Complexity Tracking и принимается человеком. Этап analyze считает нарушение конституции
критичным замечанием.

Изменения вносятся через `/speckit.constitution` с описанием причины. Версия растёт по правилам
семантического версионирования: MAJOR — удаление или переопределение принципа, MINOR — новый
принцип или существенное расширение, PATCH — уточнение формулировок. Соблюдение проверяется на
каждом этапе цикла (Constitution Check в plan) и скриптом `scripts/check.sh`.
